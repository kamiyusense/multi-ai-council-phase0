# Claude Loop (Claude only) — how to give it work

日本語の要約：Julesを使わない、Claudeだけの自動Loop。`[claude loop] ` で始まるIssueに依頼を書くと、作業係のRoutineが受け付けて実装し、PRを出す。検査係のRoutineがPRを毎回チェックして、ダメなら作業係が直す（最大2回）。合格したPRはオーナーのMerge待ちで並ぶ。Mergeはオーナーだけ。止めたいときは #494 を閉じる。

This loop replaces the Claude x Jules loop (prod-c1, control issue #346), which the owner ended on 2026-10-30 (Jules is
read-only from 2026-11-11 and ends on 2026-12-31). It keeps that loop's proven parts: GitHub as the only state, the
`claude-closed-loop-task v1` / `claude-closed-loop-receipt v1` records, the reviewer's three layers, the stop switch
and the checkpoints. Jules, its labels, the Jules API and the LIVE budget files are gone.

## What the loop is

| Part | Where |
|---|---|
| Policy: scope, limits, forbidden paths, expiry | [`active/policy.json`](active/policy.json) |
| Control issue: checkpoints and stop switch | [#494](https://github.com/kamiyusense/multi-ai-council-phase0/issues/494) |
| Work queue | open issues titled `[claude loop] ...` with a request block |
| Queue rules (deterministic) | [`automation/command_bus/claude_only_loop.py`](../../automation/command_bus/claude_only_loop.py) (`next`, `accept`, `refuse`, `show`, `checkpoint`) |
| Worker | Routine "Claude Loop worker" (the former "Claude takeover worker"). Prompt: [`worker-routine-prompt-v1.txt`](worker-routine-prompt-v1.txt) |
| Reviewer | Routine "Claude Loop reviewer" (the former "Claude closed-loop reviewer v1"). Prompt: [`reviewer-routine-prompt-v1.txt`](reviewer-routine-prompt-v1.txt) |

One task at a time:

```text
[claude loop] issue opened -> worker wakes -> `next` says START -> `accept` posts the task block (one, ever)
  -> worker implements on claude/loop-<issue>, runs the tests, opens a PR "Fixes #<issue>"
  -> reviewer wakes on the PR -> receipt on the issue: PASS / NEEDS_CORRECTION / BLOCKED
  -> NEEDS_CORRECTION: the worker's next wake (`next` says CORRECT) fixes it on the same PR (up to 2 rounds)
  -> PASS: the PR waits for the owner's merge; the next request starts
  -> anything after round 3, or BLOCKED: TASK_BLOCKED, the owner looks
```

Limits (policy): 10 new tasks per UTC day, 10 files per task, ADD/MODIFY only, existing tests read-only, 2 correction
rounds, a worker or reviewer with no progress for 120 minutes is reported on #494, expiry 2026-12-31T15:00:00Z
(2027-01-01 00:00 JST).

## Give the loop a task (any AI or the owner)

Open an issue under the owner's account (Grok via Cursor, Claude, Codex, or by hand) titled `[claude loop] <summary>`:

```text
goal: what to change and why (evidence: a failing test, an error, a measured gap)
allowed_paths:
- path/to/file.py (MODIFY)
- path/to/test_new_check.py (ADD)
acceptance:
- a checkable statement
- a regression test that fails without the change
test_commands:
- python3 -m unittest path.to.test_new_check

AI-Agent: grok
```

The loop refuses (one comment, never processed again): another author, no `AI-Agent:` (or `Generated by Claude
Code`) line, a missing field, a delete or rename, more than 10 files, a modified existing test, and every forbidden
path in the policy (`.github/`, `.claude/`, `AGENTS.md`, `CLAUDE.md`, `src/relay/`, `src/providers/`, safety-boundary
and Jules files, records and ledgers, dependency and Docker files, `*.cmd`/`*.ps1`, and the loop itself). Research
questions (`mode: research`) go to the contractor routine, not here. The full suite always runs in addition to
`test_commands`.

## Watch, stop, merge

- Progress: the latest `claude-loop-checkpoint v1` comment on #494 (`action`, `tasks`, `human_required`).
- Stop: close #494 or give it the `loop-stop` label. New starts and corrections stop; reviews of pushed work continue.
- Merge: owner only, at the head the PASS receipt names (`pr_head_sha`). A loop PR without a PASS receipt is never
  merged.

## Who may write loop records

The owner's GitHub account is shared by every AI that writes for the owner (Grok via Cursor, Claude, Codex). So a
loop record (accept, refusal, receipt, checkpoint) counts only when the owner's account wrote it through the Claude
GitHub App (`record_apps` in the policy, read from `performed_via_github_app`). A record that came through any other
app, or was typed by hand, puts that task in RECORD_UNREADABLE: the owner looks, and the loop neither trusts it nor
re-does the work.

## UNKNOWN until first use

- That the Routines' writes carry `performed_via_github_app = claude` (Claude sessions' comments did on #459). If they
  do not, the first task stops at RECORD_UNREADABLE (nothing is accepted twice) and `record_apps` is corrected by PR.

- Whether an issue opened by the Claude GitHub App wakes the worker (a contractor test issue did not, a Cursor one
  did). The hourly recovery schedule covers it.
- GitHub event delivery is capped per Routine and per hour; a dropped event is picked up by the schedule.
- The cloud environment's pytest: without it `python3 -m pytest -q tests` is NOT RUN, never installed.

## Rules carried by every handover

AGENTS.md safety defaults apply. No Routine, settings, secret, permission or billing change and no merge without the
owner's explicit approval. An unknown write outcome is read back, never resent. Unknown is written as UNKNOWN.
Text the user pastes elsewhere is one `markdown` code block ([format](../USER_COPY_TEXT_FORMAT.md)).
