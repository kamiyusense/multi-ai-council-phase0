# Relay / Control Tower direction V4 (owner-approved 2026-10-23)

Status: owner-approved plan (2026-10-23 01:13 JST, project thread "Relay/Tower 新方針の変更計画").
This file records the decisions; the Japanese plan for the owner is [`RELAY_TOWER_PLAN_V4_JA.md`](RELAY_TOWER_PLAN_V4_JA.md) (same content). Each step lands as its own PR; every Merge still needs the owner's
explicit chat approval. It does not authorize any LIVE run, billing, permission or settings change.

## 1. Records and boards

- The durable record stays in repository files / dedicated branches. Issues (#33 and others) are boards,
  never the source of truth.
- Boards follow the Renovate Dependency Dashboard shape: the Issue body is regenerated on every run, and the
  owner's checkboxes and approval comments on it are read by the Control Tower and reflected into the record.

## 2. Writers, signatures and approval

- No new key, PAT or GitHub App. AI writers (Claude, Grok Bot via the Cursor GitHub integration, Codex,
  Antigravity) write under the owner's account `kamiyusense`. Jules commits as `google-labs-jules[bot]`.
- GitHub Actions (`GITHUB_TOKEN`, `github-actions[bot]`) is used only for scheduled/automatic chores:
  regenerating boards and reading approval comments. Writes made with `GITHUB_TOKEN` do not start other
  workflows (except `workflow_dispatch` / `repository_dispatch`); a run must finish its own work or call
  `workflow_dispatch` explicitly.
- **Every AI write carries a signature.** Comments, Issue and PR bodies, and commit messages:

  | Writer | Signature |
  |---|---|
  | Claude | `Generated by Claude Code` or `Generated with [Claude Code]` (existing footers) |
  | Grok | `AI-Agent: grok` |
  | Codex (including Symphony's Codex) | `AI-Agent: codex` |
  | Antigravity | `AI-Agent: antigravity` (requested in the Relay-generated paste template) |
  | Actions on behalf of an AI | `AI-Agent: <name>` of the requesting AI |

- **An AI never writes the word 承認 on its own** (as the whole body or as a standalone line). Use it only inside
  longer words or phrases (承認待ち, 承認コメント).
- **Human approval** is a comment that meets all of:
  1. author is user id `20355232` (`kamiyusense`);
  2. body is exactly `承認` (surrounding whitespace, newlines and a trailing `。` allowed);
  3. contains no signature from the table above;
  4. was never edited (`created_at == updated_at`);
  5. was written after the proposal it approves, and the target still matches (for a PR: the same head SHA);
  6. is used once; its use is recorded in the durable record.
  Anything else (other authors, `github-actions[bot]`, signed comments, 承認します, OK) is not an approval.
- Signatures are a convention, not something GitHub enforces. Writers built in this repository refuse to post
  an unsigned body or a bare 承認 (pre-write check, step S2). Grok Bot and Antigravity rely on their prompts.
- Merges are unchanged: an AI asks in chat, the owner answers in chat, and the merge note says
  `approved by kamiyusense (chat approval)`. This is separate from the 承認 comment rule.
- The private free-plan repository cannot enforce required approvals with branch protection; the checks
  live in the workflows.

## 4. Relay and Council

- Relay runs on the owner's PC, not in the cloud. Council = Grok, Claude, Codex through their official CLIs
  with subscription sign-in (Grok: `grok --no-auto-update agent stdio` or `grok -p`; `XAI_API_KEY` must
  never reach the child process).
- Antigravity flow: Relay writes a Markdown paste template (question + answer format); the owner pastes it into
  Antigravity by hand; the answer is pasted back or written by Antigravity to a fixed GitHub location that
  Relay reads. Relay merges four answers plus the owner's view.
- Lines that hold: no tool launches, drives or wraps Antigravity; nothing writes the next instruction where
  Antigravity reads (the answer location and any instruction location are separate, one-way); Antigravity's
  internal files (`~/.gemini/`, transcripts) are never read, only its outputs (PRs, Issues, project files).
- The Antigravity launch code is moved to `archive/antigravity_launch/` and disabled (step S1), with the header
  "suspended, do not run (terms, 2026-10)", so it can be restored if the terms change. The launch deny-list
  (`LIVE_ADAPTER_MARKERS`) stays active.
- Grok terms (owner's research): xAI's announcement (https://x.ai/news/grok-build-cli) states headless `-p`
  use in scripts and automation and ACP use for custom bots and orchestration apps; the docs
  (https://docs.x.ai/build/cli/headless-scripting) show an ACP client with the cached subscription sign-in.
  Forbidden: evading usage limits and sharing credentials. Running it on a schedule next to Claude/Codex is
  not described (UNKNOWN). Grok CLI shares the weekly quota with the Grok app and Grok Bot.

## 5. Director role and takeover

- The director is a role, not a fixed AI. All state lives in the durable record so any AI can resume.
- Fallback order lives in a config file (for example Claude -> Codex -> Grok CLI). Antigravity is never a
  candidate.
- One director at a time: an owner lock with generation fencing (reuse `loop_owner.py`,
  `claude_jules_handover.py`, `runtime_takeover.py`), takeover after a timeout, a handover note, and a
  Japanese report to the owner.
- A stand-in director may only do static work (no code change) and status reports, with a daily cap. No code
  change, Merge or production setting change by a stand-in.

## 6. Quota

- No fixed limit values: read the remaining percent through official means on every run (Claude Code
  statusLine `rate_limits`, Codex app-server rate limits). A plan upgrade is seen at once.
- Never spend quota to read quota (no asking a model for its remaining usage).
- Unreadable quota pauses only that AI; the board shows "枠が不明なので休止中" and the owner's
  "続けて OK" resumes it. Other AIs keep running.
- Grok has no known official programmatic reading (UNKNOWN): a weekly run cap, one number in the config file.
- Extra credits are off by default; only an owner approval like "今週はクレジットを使っていい" allows them, within
  that scope. Auto top-up is never assumed.
- Changing `on_quota_unknown` of the running campaign `prod-c1` needs a separate owner approval.

## 8. Wake after a merge (documentation fix)

`claude_jules_loop.py` labels the MERGE_WAIT wake as "pull_request.closed (merged) event", while
`CLAUDE_JULES_API_ROUTE_V1.md` records that the Routine is not woken by `pull_request.closed`. Which GitHub
events the Routine listens to is a Routine UI setting and cannot be read from the repository (UNKNOWN). What
is certain: the reviewer Routine also runs hourly at :02, so merge-dependent work resumes within about one
hour after a merge. The loop code is left unchanged (the Claude x Jules loop stays as is); read its
`next_wake` label as "the merge event if the Routine is configured for it, otherwise the hourly run".
