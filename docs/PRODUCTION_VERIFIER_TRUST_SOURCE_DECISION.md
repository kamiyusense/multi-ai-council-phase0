# Production verifier trust-source decision boundary

## Status

Date: 2026-09-29 JST

Repository:
`kamiyusense/multi-ai-council-phase0`

This document records the trust-source boundary only.

It does not change workflow permissions, request an OIDC token, create an
attestation, authenticate a provider, issue owner authority, execute Jules, or
mutate Issue #33.

## Existing repository requirement

The merged verifier framework intentionally requires an independently injected
`VerificationSourceAuthenticator`.

A normalized source document is transport material only.

The following are insufficient by themselves:

- GitHub JSON presence;
- a source field saying `verification_state=VERIFIED`;
- a successful GitHub Actions conclusion;
- a Jules Session JSON response;
- a command/receipt/evidence record generated by the same controller being
  verified.

The authenticator must establish trust independently from the material whose
contents are being asserted.

## Candidate A — GitHub Actions run/job/log readback

GitHub's REST API can expose workflow-run/job/log metadata read-only.

For public repository resources, the documented run/job endpoints may be read
without authentication. With authenticated fine-grained tokens, Actions
repository permission READ is the relevant permission.

### What this can prove usefully

Readback can corroborate transport facts such as:

- exact repository;
- workflow identity;
- run/job identity;
- head SHA;
- event;
- conclusion;
- timestamps;
- logs/artifacts produced by that workflow.

### What this does not prove by itself

A readback of GitHub-hosted metadata is not automatically an independent
cryptographic attestation of the Jules/provider facts embedded inside a log or
JSON document.

Therefore the safe classification is:

`GITHUB_ACTIONS_READBACK = TRANSPORT_EVIDENCE_ONLY`

It may be used as source-reader material, but this document does not authorize
treating it as the production `VerificationSourceAuthenticator`.

No extra permission is added for this option.

## Candidate B — GitHub Actions OIDC

GitHub documents an OIDC token issued to an Actions job. The token contains
signed claims about the workflow execution context.

The workflow/job must grant:

`id-token: write`

GitHub documents that this permission enables requesting the OIDC JWT and does
not itself grant write access to other GitHub resources.

### Advantages

A correctly verified token can cryptographically bind execution context such as
the repository/workflow/run/ref/SHA claims rather than trusting a controller
JSON field.

### Boundary

Adding `id-token: write` is still a workflow permission change in this
project's approval model.

Therefore:

`GITHUB_OIDC_AUTHENTICATOR = CANDIDATE / NOT_AUTHORIZED`

No OIDC workflow modification is made in this batch.

## Candidate C — GitHub Artifact Attestations

GitHub Artifact Attestations can establish signed build provenance.

GitHub's documented workflow permissions for generating an attestation include:

- `id-token: write`
- `contents: read`
- `attestations: write`

### Advantages

This is the strongest GitHub-native provenance option considered here for an
artifact/source document whose digest can be made the attested subject.

### Boundary

It requires additional write permission and an attestation-generation step.

Therefore:

`GITHUB_ARTIFACT_ATTESTATION = STRONG_CANDIDATE / NOT_AUTHORIZED`

No attestation permission or action is added in this batch.

## Provider-specific Jules fact

The current Jules Session GET adapter can normalize:

- exact session id;
- provider createTime;
- provider updateTime;
- raw provider state;
- exact durable loop/generation/target/evidence context.

It deliberately does not claim that the normalized document authenticates
itself.

A production solution still needs an independent root of trust proving that the
observed Session GET material came from the trusted execution path and was not
self-asserted by the same controller.

## Safe default

Until an explicit trust-source choice is approved:

```text
normalized Jules provider source
+ GitHub Actions readback
= useful evidence
!= independent authenticator

provider authenticator = NOT_WIRED
authority authenticator = NOT_WIRED
RuntimeTransitionPublisher = fail closed before owner/runtime writes
```

Do not weaken the verifier contract merely to make the Control Tower reach
DURABLE/READY.

## Recommended next decision boundary

The next human/architecture approval should choose between:

1. keep the current production path NOT_WIRED while using read-only Actions
   evidence only for diagnosis/testing; or
2. authorize a narrowly scoped signed trust mechanism, with GitHub OIDC as the
   smaller permission change and Artifact Attestation as the stronger provenance
   mechanism when an attestable artifact/digest is appropriate.

The exact authenticator must still verify bounded context and must never expose
tokens, credentials, or private session URLs in durable public records.

## Explicitly not performed

- no workflow permission changes;
- no `id-token: write`;
- no `attestations: write`;
- no OIDC token request;
- no artifact attestation;
- no production authenticator;
- no authority grant issuer;
- no Jules/provider/model execution;
- no runtime durable write;
- no Status dispatch;
- no Issue #33 mutation;
- no PLACEHOLDER -> DURABLE promotion.
